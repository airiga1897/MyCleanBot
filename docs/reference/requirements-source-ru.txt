# Технические требования к проекту Django

## 1. Архитектура и организация кода

- **Service Layer** — вся бизнес-логика выносится из views и моделей в отдельные сервисы.
- **Repository Pattern** — для сложных запросов, выходящих за рамки стандартного Django ORM.
- **DTO/Schemas** — использование Pydantic или dataclasses для валидации данных на границах сервисов.
- **Abstract Classes & Mixins** — переиспользование логики через абстрактные классы и миксины (без множественного наследования моделей).
- **Type Hints** — все функции и методы аннотированы типами; проверка через mypy в CI.
- **Строгий DRY** — дублирование кода более 3 строк (кроме конфигов) требует обоснования.
- Кроссплатформеннось
- Если есть Celery, то в dev локально на Windows должно быть в solo

## 2. API

- **Версионирование** — `/v1/`, `/v2/` в URL.
- **RootAPI** — базовая авторизация на процессе отладки (только для dev-режима).
- **Стандартные ошибки** — формат по RFC 7807 (Problem Details).
- **Пагинация** — единый формат: `{"count": 10, "next": "...", "previous": "...", "results": []}`.
- **Сортировка и фильтрация** — через query params (например, `?sort=-name&status=active`).
- **Документация** — Readoc + Swagger (генерируется из кода, без ручных правок).

## 3. Аутентификация и безопасность

- **JWT** — access + refresh токены.
- **Rate limiting** — отдельно для аутентифицированных и неаутентифицированных запросов.
- **Request size limits** — глобально и для отдельных эндпоинтов.
- **CSP (Content Security Policy)** — настроенные заголовки.
- **Санитизация входных данных** — явные списки полей, `allow_blank=False`, валидация на схеме.
- **Безопасное логирование** — никаких паролей, токенов, email, phone в логах.

## 4. Код и стиль

- **Запрещены `print()`** — только через `logging.getLogger(__name__)`.
- **Запрещены голые `except:`** — всегда указание класса исключения.
- **Запрещены `**kwargs` и `*args` без явной аннотации допустимых значений**.
- **Любая функция длиннее 15 строк** — требуется разделение или обоснование на ревью.
- **Naming convention**:
  - `get_*` — не изменяет состояние
  - `create_*` — возвращает ID или объект
  - `_internal_*` — приватные методы

## 5. Тестирование

- TDD - подробно описать
- **Фреймворки** — pytest + unittest для каждого Django-приложения.
- **Аутентификация в тестах** — запрещён `force_login`; только реальная JWT.
- **Тесты на идемпотентность** — для PUT, DELETE, PATCH.
- **Фикстуры** — через `factory_boy` (запрещены `dumpdata`-фикстуры).
- **Покрытие** — не менее 95% на критическую логику (auth, payments, API), в идеале - 100%.
- **Mutation testing (опционально)** — для модулей с финансами/персональными данными.

## 6. Отказоустойчивость

- **Отсутствие fallback в основном коде** — никаких `try/except` без явной обработки ошибок выше уровня сервисов.
- **Health check** — эндпоинт `/health/` с проверкой БД, кеша, JWT.
- **Идемпотентность** — важные операции (платежи, обновления) защищены идемпотент-ключами.

## 7. DevOps и окружение

- **12-factor app** — конфигурация через env, логи в stdout/stderr.
- **Миграции** — отдельный этап деплоя с проверкой обратной совместимости.
- **Pre-commit хуки** — black, isort, flake8 (с правилами из `.flake8`).
- **No root code execution при импорте** — инициализация только внутри функций/классов.

## 8. Организационные требования

- **Code owners** — для `auth/`, `payments/`, `core/security/`.
- **Каждый PR** — проходит линтеры, mypy, тесты.
- **Pull Request Template** — обязательные пункты: что сделано, как тестировалось, breaking changes.
